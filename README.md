# PipeTracker — учёт замеров труб НКТ при СПО

Android-приложение для бурильщика/мастера бригады КРС: электронный журнал замеров
длины труб при спуско-подъёмных операциях вместо бумажного. Замеряет каждую трубу,
компоновку низа (BHA) и переводники, считает нарастающую длину колонны, группирует
по диаметрам и экспортирует в Excel (XLSX).

## Стек

- Kotlin, Jetpack Compose (Material 3), MVVM + Repository + Room
- Navigation Compose, Coroutines/Flow
- Apache POI 5.2.5 (XLSX)
- KSP (не kapt), Room 2.6.1
- `minSdk = 26`, `compileSdk`/`targetSdk = 34`, Java 17
- AGP 8.5.2, Kotlin 1.9.24, Compose BOM 2024.06.00, Gradle 8.7

## Бизнес-логика (ключевые решения)

- **Иерархия**: СПО → ряды → трубы; переводники внутри ряда; компоновка внутри СПО.
- **Нумерация труб** — сквозная по всей СПО «от забоя вверх»: самый старый ряд
  (по `createdAt`) получает наименьшие номера, внутри ряда — по `indexInRun`.
- **Нарастающая длина** считается от забоя (от компоновки) и не сбрасывается на
  границах рядов и при смене типоразмера:
  `withBha = bha_total + pipes_and_equipment_in_current_run_up_to(pipeIndex)
           + pipes_and_equipment_in_all_earlier_runs`.
  У каждой трубы два числа: `pipesOnly` (без компоновки) и `withBha` (с компоновкой).
- **Переводник** не участвует в нумерации труб, отображается отдельным списком
  под трубами ряда, в экспорт идёт только на лист «Оборудование».
- **Вставка трубы** после любой существующей — атомарная транзакция
  (`db.withTransaction`): сдвиг индексов труб `+1`, сдвиг `afterPipeIndex`
  переводников `+1`, вставка новой трубы — переводник остаётся привязан к той же
  физической трубе. Удаление трубы симметрично пересчитывает индексы и «перевешивает»
  переводник на предыдущую трубу.
- **Текущая СПО** — выбор пользователя, хранится в `SharedPreferences`
  (`currentSpoId`), а не «единственная незавершённая в базе». `isCompleted` — просто
  пометка, завершённую СПО можно продолжать редактировать.
- **Активный ряд** — `ensureActiveRun(spoId)` под `Mutex` с suspend-проверкой к БД
  внутри одной защищённой операции (защита от гонки из параллельных
  `LaunchedEffect`). Завершение ряда автоматически открывает следующий ряд той же СПО:
  экран реагирует на переход активного ряда в `null`, а не только на разовую
  инициализацию.
- **Пресеты** — «НКТ 60/73/89/102/114», «СБТ 2 3/8», «СБТ 2 7/8». Дедупликация в
  `Callback.onOpen`: сначала `DELETE ... WHERE id NOT IN (SELECT MIN(id) ... GROUP BY name)`,
  затем `INSERT ... WHERE NOT EXISTS` — при каждом открытии БД, без дублей. Порядок —
  по добавлению, не по алфавиту.

## База данных и миграции

- `version = 8`, `exportSchema = true`.
- `.fallbackToDestructiveMigrationFrom(1, 2, 3, 4, 5, 6)` — старые версии без ценных
  данных можно стереть. **Безусловный** `fallbackToDestructiveMigration()` не
  используется: с версии 7 любое изменение схемы обязано сопровождаться настоящей
  `Migration` в `MIGRATIONS`, иначе приложение падает при открытии БД.
- `MIGRATION_7_8` — приёмка п.7: версия поднята с 7 до 8, в `spo` добавлено тестовое
  поле `testField TEXT NOT NULL DEFAULT ''`. Установка новой сборки поверх существующей
  базы с данными сохраняет все СПО/ряды/трубы.
- Миграция проверяется тестом `MigrationTest` (Robolectric + `room-testing`, без
  эмулятора). Схема `7.json` восстановлена по `8.json` минус `spo.testField` —
  настоящая схема 7 в репозитории не сохранилась. Схемы подключены ассетами только
  в debug-сборку (`sourceSets.debug.assets`).
- **Версии 1–6:** миграций нет (схемы 6/7 не сохранились), Room пересоздаёт базу
  пустой. Перед этим `LegacyDbGuard` сохраняет полную копию старого файла в
  `filesDir/legacy_backup/uchet_v<N>_<дата>.db` (если копия не удалась — приложение
  падает при запуске, данные остаются на месте). Файл можно отправить из
  «Настройки → Данные старой версии»; по нему пишется настоящая миграция.
- Unit-тесты запускаются только в debug-варианте (`testReleaseUnitTest` отключён:
  схемы Room лежат в debug-ассетах).

## Экспорт в Excel

Один файл = одна СПО (кнопки «Просмотр» / «Отправить» у каждой СПО на экране
«Выбор СПО»). Один лист «Отчёт», A4 книжная, подгонка по ширине страницы.

- **Шапка**: «ОТЧЁТ о состоянии и замере насосно-компрессорных труб»,
  «Куст № … Скважина № … Месторождение: …», СПО и дата начала, подрядчик/бригада
  (заглушки), компоновка с длиной и составом, сводка по типоразмерам,
  **список переводников и оборудования** (тип, размер, длина, после какой трубы),
  итоги: длина труб, с оборудованием, с компоновкой (`totalWithBha`).
- **Таблица труб сгруппирована по типоразмеру** (порядок — первое появление в
  колонне). У группы своя нумерация «№ п/п» с 1 и свой счётчик **блоков по 10**:
  после каждого блока строка «Блок N (№a–b), k шт.: сумма». В конце группы —
  «Итого {типоразмер}».
- **Двухколоночная вёрстка**: 6 колонок × 2 (№ п/п, Диаметр, Марка стали,
  Длина трубы, Длина колонны, Примечание). До 100 труб группы на страницу:
  блоки 1–5 слева, 6–10 справа; дальше разрыв страницы и «(продолжение)».
- **Переводник не строка таблицы**: он в шапке и в «Примечании» трубы, после
  которой стоит.
- «Длина колонны» у трубы — компоновка + все трубы СПО по эту трубу в физическом
  порядке, без оборудования (как раньше). Итог с оборудованием — в шапке.
- Внизу: «Мастер ТКРС», дата, ФИО, подпись.

Поля, которых нет в модели данных («Марка стали», «Подрядчик», «Бригада №»,
«ФИО мастера»), выводятся пустыми заглушками.

Имя файла — `дата_скв№_название_idN.xlsx` (id СПО делает имя уникальным).
Файл кладётся в `cacheDir/exports` и отдаётся через `FileProvider`
(просмотр / отправка через `ACTION_VIEW` / `ACTION_SEND`).

## Отмена удаления и резервная копия

- Удаление трубы («Замер», «Редактирование ряда») и СПО («Выбор СПО») —
  snackbar «Отменить» на 5 секунд. Перед удалением снимается снимок данных,
  отмена восстанавливает его в транзакции с исходными id. Удаления ряда в
  приложении нет.
- «Настройки → Сохранить копию базы (.db)»: `PRAGMA wal_checkpoint(FULL)`, затем
  копия `uchet.db` в `cacheDir/exports` и отправка через `ACTION_SEND`.
  Восстановление из копии в приложении не реализовано.
- Длина трубы > 20 м (`MAX_REASONABLE_PIPE_M`) — на «Замере» диалог
  подтверждения, в редакторе трубы — подсветка поля.

## Примечания по Compose (грабли, которые уже срабатывали)

- В списках, объединяющих элементы из разных таблиц (трубы + переводники в одном
  `LazyColumn`), ключи включают префикс таблицы: `"pipe_${id}"` / `"crossover_${id}"` —
  иначе автоинкрементные id из разных таблиц совпадают и Compose падает с
  `IllegalArgumentException: Key already used`.
- Диалоги «из списка или свой вариант» (типоразмер, тип оборудования) при выборе
  «Свой» показывают текстовое поле для ввода значения, а не молча сбрасывают выбор
  в пустую строку.

## Проверка приёмки (ручной сценарий)

1. Создать две СПО («Спуск пера», «Спуск пакера», разные даты) через «Выбор СПО»;
   переключаться между ними — замеры не теряются и не путаются.
2. В одном ряду ввести трубы двух типоразмеров подряд, добавить между ними переводник —
   он не нумеруется как труба, но входит в нарастающую длину.
3. «Трубы СПО» → редактировать ряд → вставить трубу в середину после трубы с
   переводником — переводник останется привязан к той же физической трубе.
4. На экране «Замер» завершить ряд — сразу откроется следующий ряд той же СПО, ввод
   длины продолжает работать.
5. «Трубы СПО» — накопленные длины монотонно растут; два числа (с компоновкой и без)
   согласованы.
6. Экспортировать обе СПО по отдельности — два файла (разные имена), без смешения данных.
7. Поднять версию БД на 1 с тестовым полем и `Migration`, установить поверх старой
   базы — все данные сохраняются (реализовано: `MIGRATION_7_8`).
8. Пресеты типоразмеров не задваиваются при повторных запусках (дедупликация в
   `onOpen`).
